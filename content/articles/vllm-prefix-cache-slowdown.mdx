# 一次批量推理变慢的排查：为什么提示词能复用，模型却还在重复计算

## 1. 问题是怎么出现的

我们有一个商品质量离线审核任务，用大模型检查商品标题、短描述和详细描述。任务从 ODPS 读取数据，在 8 个 H20 worker 上运行，通过 vLLM 做批量推理，再把审核结果写回表里。

问题出现在模型从 Qwen3.6 切换到 Qwen3.8 之后：同样的输入表、同样的 worker 数，每个 worker 的吞吐从约 5.92 行/秒降到了 3.44 行/秒，下降约 42%。这意味着相同规模的数据需要更长时间才能处理完。

这次切换也伴随提示词变化，所以一开始不能直接认定是新模型本身慢。我们需要分清楚：是引擎配置不合适、缓存没有发挥作用，还是每条请求需要做的计算确实变多了。

最终，我们定位到前缀缓存的复用粒度过大。调整状态缓存精度、配合修改短描述提示词后，对照运行的吞吐达到约 8.48 行/秒，是修复前 3.66 行/秒的 2.33 倍。另一轮使用更高并发的完整运行也顺利结束，吞吐约 8.2 行/秒。

## 2. 先看每条请求到底多做了什么

三类审核任务都有固定的规则提示词，变化的只是后面的商品内容。按预期，同一类请求应该能复用前面已经算过的部分，这就是前缀缓存的作用。

我们把监控拆开看，没有只盯着总耗时和缓存命中率。

| 每条请求的平均指标 | 切换前 | 切换后 |
|---|---:|---:|
| 输入长度 | 约 1305 token | 约 1898 token |
| 复用缓存的输入 | 约 771 token | 约 745 token |
| 仍需计算的输入 | 约 534 token | 约 1153 token |
| 输出长度 | 约 56 token | 约 54 token |
| 吞吐 | 5.92 行/秒 | 3.44 行/秒 |

输出长度基本没变，输入侧需要计算的 token 却翻了一倍多。这里最值得追问的现象是：**提示词明显变长了，为什么缓存复用量还停在七百多个 token？**

缓存命中率从 59% 降到 39%，单看这个比例容易理解成缓存“丢得更多了”。但绝对命中量几乎不变，也可能是可复用的长度遇到了某个上限。我们接下来就围绕这两种解释排查。

本文把“没有命中缓存、需要正常计算的输入”称为“未缓存输入”。它和监控中“请求被抢占后重新计算”的计数器是两回事，不能混用。

## 3. 先验证并发和显存，再检查请求本身

最先检查的是并发是否太高，导致显存紧张，进而影响缓存。

我们把并发从 384 降到 256。KV Cache 使用率从 67% 降到 46%，单请求延迟和排队时间都有下降，但吞吐只提升了约 1%，每条请求复用的 token 也仍然是七百多个。

这说明在这组实验里，降低并发释放出的显存没有解决问题。继续围绕显存容量调参，缺少收益依据。后来修复缓存问题后，我们又把并发从 256 提到 512，吞吐反而下降约 3%，也没有得到预想中的提升。因此，最终保留了 256 的并发配置。

另一个方向是数据和请求组织方式：三类任务交错运行，会不会影响缓存复用？提示词中间是否混入了商品变量，导致看起来一样的前缀实际上不一样？

我们检查了提示词的构造方式。同一任务类型的 system prompt 是模块级常量，商品内容放在后面，共享前缀确实存在。数据组织方式也没有提供足够证据解释这次变化。

到这里，问题进一步收窄：请求本身具备复用条件，降低缓存压力又没有改善命中量，需要看引擎究竟按什么规则复用前缀。

## 4. 转折点：缓存只能整块命中，而一块有 1568 token

我们用仓库里已有的 tokenizer 工具测量了三类公共提示词的长度，再去对照引擎启动日志和源码。

原始记录包含几轮提示词版本，具体长度略有变化。以下采用修复前验证阶段的数据：标题审核约 2618 token，短描述约 724 token，详细描述约 862 token。

随后在 vLLM 的启动日志中发现了一条关键配置：

```text
Setting attention block size to 1568 tokens to ensure that attention
page size is >= mamba page size.
```

也就是说，这次运行的缓存块大小是 **1568 token**。查看源码后确认，前缀缓存按完整块复用，不足一块的部分不能命中。

把提示词长度放进去，现象就能解释了：

| 任务 | 公共前缀长度 | 按 1568 token 分块，可复用多少 |
|---|---:|---:|
| 标题审核 | 2618 | 1568，剩余部分仍需计算 |
| 短描述语法 | 724 | 0 |
| 详细描述语法 | 862 | 0 |

短描述和详细描述合计约占 52% 的请求，它们的固定提示词连一块都凑不够。标题审核虽然能命中，但也只能命中一块。

这也解释了旧版本为什么看起来更快。旧版标题提示词约 1601 token，新版虽然变长，却仍然没有达到两块所需的 3136 token。两版都只能复用 1568 token，新增内容几乎都落在需要逐条计算的部分。

**缓存粒度的限制此前就存在，提示词增长放大了它的成本。** 按标题请求约 48% 的占比估算，平均命中量约为 `48% × 1568 ≈ 753 token`，与监控中的七百多个 token 接近。

## 5. 1568 从哪里来，又怎么证明它就是原因

1568 并不是我们手工配置的。进一步检查模型配置发现，这个模型使用混合注意力架构：64 层中，16 层是完整注意力，48 层是线性注意力。

完整注意力层保存 KV 缓存；线性注意力层保存用于继续计算的状态。在当时使用的 vLLM 实现中，开启前缀缓存后，这两类缓存需要按边界对齐，注意力缓存页还必须满足状态页的大小要求。

当时线性注意力状态使用 float32 保存，一份状态连同相关内容约为 3.21 MB；注意力层每个 token 的 KV 约占 2048 字节。按引擎的对齐公式计算，需要向上取整到 16 的倍数，最终就是 1568 token。模型配置、源码公式和启动日志能够相互对应。

但解释得通还不够。我们补采了 vLLM 自身的缓存命中 token、请求抢占次数和抢占后重算 token 等指标，用独立计数器验证。

验证运行得到三个结果：

1. 13 个监控窗口中，请求抢占和抢占后重算均为 0，没有观察到运行中请求因抢占而重复计算。
2. 缓存命中 token 的累计值及窗口增量都能被 1568 整除，累计值的最大公约数也是 1568，与启动日志中的块大小一致。
3. 结合当时各类前缀最多只能命中一块的条件，估算出的命中请求占比约为 49.2%，接近数据表中标题审核约 48.1% 的占比。

零抢占本身不能证明所有缓存淘汰都不存在。但它与降低显存压力无效、整块命中的计数特征、各类提示词长度一起，构成了比较完整的证据链：这次额外计算的主要来源，是固定前缀无法按当前块大小充分复用。

## 6. 修复做了两件事

第一件事是减小缓存块。

我们检查了当时实现允许调整的参数。直接指定线性注意力的块大小会被对齐逻辑覆盖；切换另一种缓存模式，算出来的块反而更大。修改 KV 精度虽也会改变块大小，但会增加 KV 显存占用，因此没有采用。

最终选择把 `mamba_ssm_cache_dtype` 从默认的 float32 改为 float16。状态存储占用减小后，引擎推导出的块大小从 1568 降到了 800。为此，我们打通了命令行参数到推理引擎的传递，并同步修改正常作业和补跑作业，避免两种作业使用不同精度。

这里有过一次实际失误：最初填写了 `bfloat16`，但当前版本的参数只接受 `auto`、`float32` 和 `float16`，导致 worker 在启动时失败。修正后，我们补了参数合法值检查和作业配置测试，让同类错误能在本地被发现。

第二件事是让短描述也跨过缓存边界。

块大小降到 800 后，标题可以复用 2400 token，详细描述可以复用 800 token，但短描述只有 724 token，仍然无法命中。因此，我们补充了三条已有规则的判定示例，把短描述公共前缀增加到 848 token。

这个做法看起来反直觉：提示词变长了，计算反而减少了。原因是新增的 124 token 让整个前缀跨过 800 的边界，后续请求可以复用完整的一块。仅看公共前缀，原来每次要算 724 token，现在只需计算未缓存的 48 token。

我们还给提示词长度加了边界检查，避免以后精简文案时不小心跌回 800 以下。不过，即使只是补充已有规则的示例，也可能影响模型判断，仍然需要做质量对照。

## 7. 验收既看速度，也看输出质量

性能验证使用同一 shard 的数据，并用两种口径交叉确认：一份来自运行日志，另一份来自 ODPS 每小时实际新增的结果行数。

| 指标 | 修复前，并发 256 | 修复后，并发 256 | 修复后，并发 512，完整运行 |
|---|---:|---:|---:|
| 缓存块大小 | 1568 | 800 | 800 |
| 每请求未缓存输入 | 1063.8 token | 264.6 token | 264.8 token |
| 缓存命中率 | 约 39% | 约 85.5% | 约 85.5% |
| 吞吐，ODPS 口径 | 3.69 行/秒 | 8.45 行/秒 | 8.20 行/秒 |

修复后，每条请求需要计算的输入减少约 75%。缓存命中累计值的最大公约数也从 1568 变成了 800，说明预期的缓存机制确实生效了。

按日志口径，同并发对照的吞吐从 3.66 提升到 8.48 行/秒，即 2.33 倍。并发 256 的这轮是对照窗口，随后被人工终止；真正完整跑完的是并发 512 的运行，8 个 worker 全部正常退出，吞吐约 8.2 行/秒。两项结果分别证明了对照收益和全量运行可行性。

质量验证不能省略，因为 float16 改变了状态存储精度。我们对相同 task_id 的结果逐条配对，并额外比较了两次 float16 运行，作为模型采样波动的参考。

标题四个审核维度的分歧率没有超过同精度重复运行的分歧率，详细描述也基本接近。这支持“没有观察到明显的判定退化”，但不能据此宣称精度变化完全没有影响。

短描述的分歧更明显：逐条分歧率为 2.172%，同精度对照为 0.898%。由于这次同时修改了短描述提示词，现有实验无法单独区分精度和示例变化各自造成的影响。

此外，我们扫描了约 128 万个任务、310 万条判定结果。非法判定值均被系统显式标记为 ERROR，占比约 0.06%，与改造前同量级；未发现替换字符或单字符长循环。

检查中也发现了少量异常偏长、重复的 reason。以标题语法 reason 超过 500 字符统计，两个 float16 运行的发生率分别约为 0.0916% 和 0.0072%。它们的并发不同，但仅凭现有对照还不能确定异常由什么因素引起。

按当时记录，reason 主要用于人工复核展示，这项问题没有阻塞上线，但需要保留跟踪。当前并发保留 256；是否为降低异常 reason 比例而调整并发，需要补充重复对照后再决定。

## 8. 这次排查留下了什么

最直接的结果是，在相同硬件规模下，消除了大量重复输入计算，使任务吞吐超过了模型切换前的水平。与此同时，我们补齐了缓存监控、参数校验和提示词边界测试，后续再遇到类似问题，可以更快判断缓存到底有没有发挥作用。

方法上，有三点值得保留。

首先，比例指标要和绝对量一起看。这次如果只看命中率下降，就容易一直追查缓存为什么被挤掉；真正推动排查的是“输入变长，命中量却几乎不变”。

其次，源码解释需要独立观测来验证。我们曾用输入量减去未缓存输入反算命中量，再拿它验证预测，实际上是在重复使用同一组数据。补采引擎自己的命中计数器之后，证据才更扎实。

最后，减少多少 token，不能直接换算成提升多少吞吐。输入预填充和逐 token 输出的成本不同，原先把两者混在一起估算，曾高估收益。针对本作业的运行数据分别拟合后，输出 token 的边际成本约为未缓存输入 token 的 6.6 倍；这个数只适用于当时的配置和负载，不能当成通用常数。

缓存修好后，输出生成的成本变得更突出。我们据此又把 JSON 输出模板改成了单行紧凑格式，希望减少模型生成的空白和格式 token。原记录估计这一步还能提升约 27%，但当时尚未上线验证，因此没有计入本次已实现的收益。
